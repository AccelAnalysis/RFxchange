# Permanent Lane Charters

These charters allow short work packets without relying on conversation memory. Every lane uses repository state from current merged `main`, reads `AGENTS.md`, the Four-Lens Program Authority, [`FOUR_LENS_OPTIONAL_ASSURANCE_AMENDMENT.md`](FOUR_LENS_OPTIONAL_ASSURANCE_AMENDMENT.md), the current delivery matrix, the machine ledger, its applicable domain authorities, and the exact packet before acting.

## Common charter

Every lane must:

- preserve the source hierarchy and stricter security/privacy rule;
- use immutable requirement IDs and an exact declared base SHA where the packet requires one;
- remain inside owned paths/domain and request shared changes through Lane 01;
- report implementation and completion truthfully from objective implementation/test evidence;
- never fabricate independent assurance, self-label work as independently `Verified`, self-authorize a defer, or rewrite original requirement text;
- communicate durable state through GitHub/repository artifacts;
- recalculate from merged `main` before merge when reconciliation is applicable; and
- stop at its packet boundary.

Independent verification is not a general completion, merge, release, deployment, tracker, or closure prerequisite. `Implemented — Not Verified` may be complete for delivery purposes under the Optional Assurance Amendment.

## Lane 00 — Control Room

Own program status, work packets, dependency/branch assignment, merge order, Shared Contract Request routing and post-merge recalculation. Coordinate release and optional assurance based on current risk and product-owner direction. Do not fabricate an independent assurance result.

## Lane 01 — Shared Exchange Platform

Own the shared participant shell, spatial context, selected-object state, generic map/marker/list/detail contracts, search/filter grammar, cross-lens return, Account utility, loading, accessibility primitives and truthfulness conventions. Do not absorb lens-specific authorization or domain lifecycles. Request Lane 06 assurance only when useful or explicitly directed.

## Lane 02 — Opportunities/RFx

Own only currently authorized RFx work packets. Consume Shared Exchange contracts and the canonical organization/AMACS/security boundaries. Do not begin a dependency-ineligible slice or fabricate opportunity data. May report bounded work complete from objective delivery evidence without waiting for Lane 06.

## Lane 03 — Intelligence

Own the dedicated Intelligence roadmap and authorized analytical projections. Separate dependency-independent work from RFx-, Resource-, Referral- and outcome-dependent work. Use only authoritative data with provenance, caveats and privacy suppression; never fabricate density or market activity.

## Lane 04 — Resources

Own provider application/status interaction, approved-provider representation, discovery, detail, service geography, resources and requests. Provider authority remains server-side and separate from payment, profile type and optional assurance. Consume Shared Exchange contracts.

## Lane 05 — Referrals

Own sender/recipient interaction, creation, lifecycle, relationship context, real privacy-safe paths and cross-lens recipient continuity. Preserve consent and minimum-necessary sharing. Do not invent a third-party subject or imply outcomes.

## Lane 06 — Optional Independent Assurance

Lane 06 is an optional, on-demand audit/assurance lane. When invoked, read authority before candidate summaries, do not implement production feature code for the implementation being audited, select evidence by requirement type, audit the exact implementation, and record findings/assurance truthfully. Lane 06 inactivity or reviewer unavailability does not block ordinary completion, merge, release, deployment, tracker progression, or workstream closure.

## Lane 07 — Integration / Cross-Lens QA

Exercise supported end-to-end journeys across lenses as integration risk warrants. Verify selected object, camera, URL and return state, domain action changes, privacy, no stale or contradictory detail, desktop/mobile, keyboard/accessibility, locales, performance and no authority leakage. Integration QA supplements implementation evidence; it no longer depends on prior Lane 06 acceptance unless explicitly required by a later bounded authority.
