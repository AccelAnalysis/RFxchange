# Permanent Lane Charters

These charters allow short work packets without relying on conversation memory. Every lane uses repository state from current merged `main`, reads `AGENTS.md`, this program authority, the current delivery matrix, the machine ledger, its applicable domain authorities, and the exact packet before acting.

## Common charter

Every lane must:

- preserve the source hierarchy and stricter security/privacy rule;
- use immutable requirement IDs and an exact declared base SHA;
- remain inside owned paths/domain and request shared changes through Lane 01;
- report implementation as `Implemented — Not Verified` until Lane 06 acts;
- never self-authorize a defer or rewrite original requirement text;
- communicate durable state through GitHub/repository artifacts;
- recalculate from merged `main` before merge; and
- stop at its packet boundary.

For any `MOB-01` through `MOB-05` packet or any work that plans, implements, reviews, reconciles, tests, or integrates the mobile Exchange composition, **every participating lane must read `docs/program/MOBILE_EXCHANGE_STAGES_1_2_AUTHORITY.md` and its linked current visual reference before acting**. Lens lanes must consume the shared mobile contracts rather than independently reinterpret the visual reference.

## Lane 00 — Control Room

Own program status, work packets, dependency/branch assignment, merge order, Shared Contract Request routing and post-merge recalculation. Do not normally implement runtime or independently certify a requirement. Publish the current batch with exact bases, dependencies and acceptance owners.

## Lane 01 — Shared Exchange Platform

Own the shared participant shell, spatial context, selected-object state, generic map/marker/list/detail contracts, search/filter grammar, cross-lens return, Account utility, loading, accessibility primitives and truthfulness conventions. Do not absorb lens-specific authorization or domain lifecycles. Submit candidates to Lane 06.

## Lane 02 — Opportunities/RFx

Own only currently authorized RFx work packets. Consume Shared Exchange contracts and the canonical organization/AMACS/security boundaries. Do not begin a dependency-ineligible slice, fabricate opportunity data, or certify Feature-ID completion.

## Lane 03 — Intelligence

Own the dedicated Intelligence roadmap and authorized analytical projections. Separate dependency-independent work from RFx-, Resource-, Referral- and outcome-dependent work. Use only accepted authoritative data with provenance, caveats and privacy suppression; never fabricate density or market activity.

## Lane 04 — Resources

Own provider application/status interaction, approved-provider representation, discovery, detail, service geography, resources and requests. Provider authority remains server-side and separate from payment, profile type and verification. Consume Shared Exchange contracts.

## Lane 05 — Referrals

Own sender/recipient interaction, creation, lifecycle, relationship context, real privacy-safe paths and cross-lens recipient continuity. Preserve consent and minimum-necessary sharing. Do not invent a third-party subject or imply outcomes.

## Lane 06 — Independent Acceptance

Read authority before candidate summaries. Do not implement production feature code. Select evidence by requirement type, audit the exact SHA, record findings and one allowed disposition per requirement, and refuse completion over substantive findings.

## Lane 07 — Integration / Cross-Lens QA

After lane-level acceptance, exercise supported end-to-end journeys across lenses. Verify selected object, camera, URL and return state, domain action changes, privacy, no stale or contradictory detail, desktop/mobile, keyboard/accessibility, five locales, performance and no authority leakage. Do not certify a missing lane-level requirement.
